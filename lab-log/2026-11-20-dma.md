# 2026-11-20 — Gen3 x8 DMA throughput (project 07)

- **Date:** 2026-11-20
- **Board:** Microsoft FPGA 1768 (Catapult v3 Longs Peak), PCB `M1003380-005`; fan on the
  heatsink
- **Host:** ASUS X99-E, BIOS 1801, i7-5820K, Windows 10 Pro 19045; card in the x8 slot on
  root port `8086:2F04`; BIOS link speed Gen3, Above 4G Decoding on
- **Toolchain:** Quartus Prime Pro 25.1.0.129. Design `projects/07_dma` (commit `f55be33`),
  `.sof` SHA-256 `BECC4D324B2FB7985E616E543F8FE10BC4ECE12A25E10ADC226CFAB4359BE77E`.
  Driver `pcie_bar.sys` 1.1.0.0 (commit `2914d91`, test-signed). Host tool `fpga1768`
  with the clock calibration of commit `1458f97`
- **Goal:** measure the host ↔ FPGA throughput limit of one Gen3 x8 link with the hard
  IP's DMA data movers, each direction alone and both at once, 4 KB to 64 MB, and prove
  the data is correct at that speed.

## What was done

1. 03:42–03:49: loaded `dma.sof` over JTAG (`quartus_pgm`, volatile, 7 min 24 s). The
   configuration flash was not touched.
2. Staged driver 1.1 (`pnputil /add-driver`, run as SYSTEM through the host's
   UnlockHelper service) without binding it, because the old device instance had no
   valid BAR after the reload.
3. Warm reboot (`shutdown /r`) so that the 64-bit BAR0 is assigned at enumeration.
4. `fpga1768 probe` with driver 1.0 still bound: BAR0 contract.
5. Bound driver 1.1 (`pnputil /add-driver … /install`, as SYSTEM): status OK, problem 0,
   driver version 1.1.0.0.
6. `fpga1768 dma info`: driver DMA state, configuration space.
7. Correctness runs (`dma run`), then the full matrix
   `dma bench --csv lab-log/2026-11-20-dma-bench.csv` (11:33:11–11:33:19), then a
   sustained run (`dma run --dir both --mode pattern --size 64M --loops 100 --repeat 60`,
   11:33:47–11:34:49).
8. Compared the FPGA 64-bit cycle counter with the host `QueryPerformanceCounter`.

### The FPGA core clock is 255.02 MHz on this host

The first simultaneous run showed `app` (host time) about 1.2 % faster than `fpga`
(FPGA cycles ÷ 250 MHz), which is impossible since the host interval contains the FPGA
interval. Comparing the FPGA 64-bit counter (BAR0 `0x74`/`0x78`) with
`QueryPerformanceCounter`:

| Interval | FPGA cycles | Host time | Clock |
|----------|-------------|-----------|-------|
| about 20 s (two tool launches) | 5,119,043,359 | 20.0789 s | 254.95 MHz |
| about 60 s (two tool launches, ~21 ms launch jitter) | 15,318,939,627 | 60.0617 s | 255.05 MHz |
| 0.5 s, in-process, bracketed reads (four runs) | | | 255.016–255.018 MHz |

The core clock is 2.5 × the PCIe reference clock, so the reference clock from this
motherboard is about **102.0 MHz**, 2.0 % above 100 MHz. Most likely cause: the board's
BCLK is set to about 102 MHz in the BIOS (hypothesis, the BIOS setting was not checked;
Windows WMI only reports the nominal 100 MHz). Consequences:

- The link runs at about 8.16 GT/s, not 8.00 GT/s; the raw ceiling is
  8.16 × 8 × 128/130 / 8 = 8.03 GB/s per direction instead of 7.877.
- GB/s computed with 250 MHz read 2 % low. The host tool now measures the clock for
  0.5 s and converts cycles with it (`1458f97`); all numbers below use the measured clock
  (255.016 MHz for the bench).
- Timing was closed for 250 MHz (+0.135 ns setup slack at 4.000 ns); at 255.02 MHz the
  period is 3.921 ns, leaving about +0.056 ns. It still passes, but with little margin.

## Interpretation

- **Single direction ≈ 7.1 GB/s each way** (88 % of the 8.03 GB/s raw rate at the
  measured clock). An estimate of the TLP limit with MPS 256 (`hypothesis`, not
  measured on the link): a memory write carries 256 bytes in about 282 bytes on the wire
  (4-DW header, sequence number, LCRC, Gen3 framing), 90.8 %; a completion 256 in about
  278, 92 %; minus ACK and flow-control DLLPs, both land near 7.1–7.3 GB/s. The
  measurements sit at that limit, so the engine and the host memory are not limiting.
- **Reads (H2D) are as fast as writes.** The 5.5–6.5 GB/s estimate for reads was too
  pessimistic; with 64 descriptors outstanding the X99 root complex returns 256-byte
  completions fast enough to fill the link.
- **Both directions: 13.03 GB/s total, D2H drops to 6.52.** The upstream direction
  carries the D2H write data and the H2D read requests (one 4-DW MRd per 512 bytes, MRRS
  512) plus the ACKs for the downstream completions, which costs D2H about 0.55 GB/s.
  A larger MRRS on the host would reduce the request overhead (not tried).
- **Small transfers are latency-bound.** `fpga` at 4 KB is 3.1 (H2D) / 4.9 (D2H) GB/s,
  `app` only 1.0–1.2 GB/s: host time is dominated by the start IOCTL and polling (about
  3 µs per transfer). The FPGA-side `data` column (Avalon beats only) saturates at
  8.16 GB/s for D2H up to 64 KB, i.e. one 32-byte beat per 255 MHz cycle.

## Result

**Success.** Gen3 x8, MPS 256, MRRS 512, 64-bit buffers above 4 GB: 7.105 GB/s host →
FPGA, 7.065 GB/s FPGA → host, 13.03 GB/s both at once, all data verified, die at most
51.7 °C. Side finding: this host's PCIe reference clock is about 102.0 MHz, not
100 MHz.
