## Lab status (2026-11-18) — BAR0 test passed

`projects/02_pcie_pio` was switched from `Avalon-MM with DMA` (Gen3 x8 256-bit) to plain
**Avalon-MM, Gen2 x8 128-bit** (`wrala_hwtcl = 7`) with a **32-bit non-prefetchable 64 KB
BAR0** and BAR1/BAR2 disabled. After a hot `pnputil /scan-devices` Windows assigned
`0xFAFF0000`–`0xFAFFFFFF`, the KMDF driver started (problem code 0), and
`pcie_bar_test.exe --write` returned `SUM 0x23456789` for `A 0x12345678 + B 0x11111111`.

What this proves: the HIP trains, the host assigns a BAR and issues 32-bit MMIO reads and
writes, and the FPGA computes the result.

If it fails: the DMA variant forces BAR0 (and BAR2) to 64-bit prefetchable memory, which
this host did not assign (problem code 10, `DEVPKEY_PciDevice_BarTypes = 0x20000`). Check
that property first; `0x100` means the 32-bit BAR made it into the bitstream. See
[lab-log/2026-11-18-pcie-pio-bar0-32bit.md](../../lab-log/2026-11-18-pcie-pio-bar0-32bit.md).

## Design

Start from the upstream `Projects/PCIe/PCIe1` project in
[tow3rs/catapult-v3-smartnic-re](https://github.com/tow3rs/catapult-v3-smartnic-re). It contains:

- `Qsys.qsys` — Arria 10 PCIe hard IP, BAR0 64 KB, PIO Avalon slave. The upstream
  file uses `wrala_hwtcl = 7`, which is **Gen2 x8, 128-bit**, not Gen3. The HIP is
  Gen3-capable, but the reference design trains Gen2.
- `Catapult_v3_PCIe1.v` — top level wiring `pcie1_rx[7:0]`, `pcie1_tx[7:0]`,
  `pcie1_perstn`, `clk_pcie1`, and `leds[7:0]` driven by the PIO output.
- `Constraints.sdc` — 100 MHz `clk_u59`, PCIe refclk, pin locations in the `.qsf`.

`projects/02_pcie_pio` in this repository uses the same board pins and, since
2026-11-18, the same HIP mode (`interface_type_hwtcl = "Avalon-MM"`, `wrala_hwtcl = 7`),
but a BAR0 register bank (`A`, `B`, `SUM`, `COUNTER`, `ID`) plus a 32 KB scratch RAM
instead of an LED PIO. In plain Avalon-MM mode the BAR0 size is derived from the address
span behind `rxm_bar0`; the scratch RAM makes it 64 KB. The earlier Gen3 x8 256-bit
variant needed `Avalon-MM with DMA`, which forces a 64-bit prefetchable BAR0 that the lab
host did not assign.

Change the vendor/device ID to something unique (e.g. `0x1234:0x0001`) before installing a
driver, so it does not collide with the Altera dev-kit IDs.

## Steps

1. Read `Projects/PCIe/PCIe1` from a scratch clone of the upstream repository; do not
   mirror it into this repository. `projects/02_pcie_pio` is an independent
   implementation generated by `make_qsys.tcl`.
2. Open Platform Designer and generate the system for Quartus 25.1 (the IP version
   changes; expect migration warnings if you start from the upstream file).
3. Compile, program the `.sof`, then **cold boot** (preferred; a hot rescan can enumerate
   the endpoint without assigning BAR0):

```powershell
# Windows
Get-PnpDevice -PresentOnly | Where-Object InstanceId -like 'PCI\VEN_1234*'
```

```bash
# Linux
sudo lspci -nn | grep 1234
sudo setpci -s 02:00.0 COMMAND=0x6      # enable memory + bus master
```

4. Map BAR0 and write a pattern:

```bash
sudo apt install pcimem
sudo pcimem /sys/bus/pci/devices/0000:02:00.0/resource0 0x0 w 0x000000AA
```

The lower 8 bits of the PIO register drive the LEDs: you should see `10101010`.

`projects/02_pcie_pio` follows the same bring-up sequence but uses a BAR0 register bank
(`A`, `B`, `SUM`, `COUNTER`, `ID`) instead of the LED PIO, and generates the system with
`make_qsys.tcl` rather than copying the upstream Qsys. See its README for the host-side
test.

## What success proves

- PCIe hard IP trains at the expected width/speed.
- The host can enumerate and access a BAR.
- The FPGA design is running (a readable ID/counter or LED reflects host access).

## Gotchas

- The HIP needs `npor=1'b1` and the dedicated 100 MHz refclk.
- After reprogramming, the host may cache the old config space. A reboot is the reliable
  way to re-enumerate.
- A hot PnP scan can enumerate the endpoint without assigning BAR0. Do **not** write BAR0
  until the command register has memory space enabled and BAR0 contains a real base
  address. An unassigned BAR0 reads `0x0000000C`; writing it through a kernel driver can
  bugcheck the host (`0x00000050` was observed with RWEverything on 2026-11-17).
- A cold boot (full AC power cycle) is the reliable way to let the BIOS assign BAR
  resources. A warm reboot may be enough if the slot keeps power, but a host crash can
  leave the card unpowered or the FT232H latched.
- If the FT232H is also absent from USB (`Present=False`, `CM_PROB_PHANTOM`), the card is
  unpowered or latched. A full AC power cycle is required; a warm reboot will not restore
  it.
- If the link trains at Gen1 only, check the refclk and the `LTSSM` state in the HIP debug
  registers.
- Windows requires a signed driver; use Linux VFIO, the Altera PCI API driver, or the
  lab's own KMDF test driver in
  [`projects/02_pcie_pio/driver`](../../projects/02_pcie_pio/driver/). The lab driver
  maps 64-bit BARs, validates the design ID before writes, and requires test signing
  with Secure Boot disabled. Linux `pcimem` remains a safe alternative.
