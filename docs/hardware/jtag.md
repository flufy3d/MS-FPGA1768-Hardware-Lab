# JTAG and the on-board USB programmer

> Status: **working** after a full VBUS power cycle (IDCODE `0x02E060DD` read 2026-11-17,
> re-read 2026-11-19). The FT232H can latch up after an aborted Quartus programmer session
> and then needs a full power cycle to recover — see the note at the end.
> Last verified: 2026-11-19

## Two ways to reach the FPGA's JTAG port

### 1. On-board FT232H (normal path)

U21 is an FTDI **FT232H** wired to the FPGA's dedicated JTAG pins, with a 12 MHz crystal
(Y2). It appears on the host as a standard FTDI USB device:

```
VID:PID  0403:6014
Driver   FTDIBUS (D2XX), "USB Serial Converter"
Location USB port 5 (on this machine)
```

The FT232H also drives the FPGA configuration pins (`nCONFIG`, `nSTATUS`, `CONF_DONE`), so
the programmer can reset the device before a download.

Quartus **does not recognise this device out of the box** — `jtagd` only looks for Altera
USB-Blaster hardware. A plugin DLL is required; see
[toolchain/onboard-usb-blaster.md](../toolchain/onboard-usb-blaster.md).

### 2. J5 external JTAG header

Standard 10-pin Altera layout:

| Pin | Signal | Pin | Signal |
|-----|--------|-----|--------|
| 1 | TCK | 2 | GND |
| 3 | TDO | 4 | VCC (1.8 V target) |
| 5 | TMS | 6 | NC |
| 7 | NC | 8 | NC |
| 9 | TDI | 10 | GND — **pull low to disable the on-board FT232H** |

Pin 10 is the important one: when the on-board programmer and an external USB-Blaster are
both connected, pull J5 pin 10 to GND to take the FT232H off the chain, otherwise the two
drivers fight.

> Cheap USB-Blaster clones are reported to be unreliable on this board; an original
> Altera/Intel Blaster or a known-good FT232H-based programmer works.

## JTAG chain

Expected on a healthy card:

```
Info:  JTAG chain detected, 1 device
Info:  Device 1: 10AX115 (IDCODE 0x02E060DD)
```

Expected IDCODE: **`0x02E060DD`**. This is the single most useful debug datum: if the chain
scans, the FPGA is alive, powered, and its JTAG pins are intact.

**On this card the chain initially did not respond** (2026-11-17). `jtagconfig`
enumerated the cable as `Microsoft Catapult (64) [USB-0]` but reported `Unable to read
device chain - JTAG chain broken`, and an independent MPSSE scan
(`scripts/jtag_mpsse_idcode.py`) read TDO stuck at `1` for every TCK speed between 100 kHz
and 2 MHz and every TCK/TDI/TMS pin permutation.

After a **full power cycle** (PSU switched off, not a reboot) the same tools read the
correct IDCODE:

```
jtagconfig
1) Microsoft Catapult (64) [USB-0]
  02E060DD   10AT115S(1|2)

python scripts/jtag_mpsse_idcode.py --speed 500000
IDCODE=0x02E060DD
OK: Arria 10 10AX115
```

So the FPGA and the JTAG wiring are fine. The failures were caused by the FT232H being in
a latched state, not by a locked or damaged TAP.

> **Recovery rule.** If JTAG reads `0xFFFFFFFF` after a programmer session (especially one
> that crashed), power the whole machine off at the PSU and back on. `FT_CyclePort`
> (`scripts/ftdi_cycle.py`) re-enumerates the FT232H but does **not** clear this latch.

## Availability of the FT232H (2026-11-19)

- The FT232H is powered from the card. When the card lost power on 2026-11-19 (thermal
  shutdown) the USB device disappeared at the same moment as the BAR0 registers started
  reading `0xFFFFFFFF`, so "FT232H absent" and "card unpowered" are the same observation.
- After an AC power cycle the device is back within a few minutes and stays present while
  a lab bitstream owns the FPGA.
- **Reported, not proven:** with the factory image running, the FT232H was present 4
  minutes after boot, but absent 15 minutes after boot while the card was still powered and
  enumerated on PCIe (`1414:B204`, Gen3 x8). That suggests the factory image disables the
  programmer. Test it with one USB check per minute before concluding; if true, program
  the FPGA within the first minutes after a cold boot.
- A killed programmer session leaves `jtagserver` wedged and every later run fails with
  `Error when scanning hardware - Server error`; see
  [troubleshooting.md](../troubleshooting.md).

## Reconfiguration behaviour

- Loading a `.sof` over JTAG clears the current FPGA configuration and replaces it
  (volatile). The config flash is not touched.
- If the application design does not instantiate the JTAG debug fabric, `jtagconfig` still
  sees the device (the JTAG TAP is always present).
- `nCONFIG` pulsing by the programmer produces a full reconfiguration from flash, which is
  how you return to the factory image without a reboot:
  `quartus_pgm --mode=jtag --operation="p;Catapult_v3_sfl.sof"` also works, but the
  simplest reset is a power cycle.

## Signal integrity

- The FT232H runs at a fixed 15 MHz TCK (in the community plugin) / 6 MHz in some builds;
  the FPGA's JTAG TAP is 1.8 V. Level shifting is on the board.
- Long USB cables are fine; the TCK is generated by the FT232H, not the host.
- If `jtagconfig` reports "unable to lock", try another USB port (the FT232H is USB 2.0
  high-speed) and make sure no serial terminal has the device open.
