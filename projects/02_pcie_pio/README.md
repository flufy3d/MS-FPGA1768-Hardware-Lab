# 02 — PCIe BAR0 compute endpoint

Minimal Arria 10 PCIe #1 endpoint with a BAR0 register bank. The host writes two
32-bit operands and reads back their sum. A free-running counter and an ID register
prove that the read path is real. **No LEDs are used** — project 01 already verified
the LED pins, and this project is about BAR0 MMIO and FPGA-side computation.

| Item | Value |
|------|-------|
| Top-level entity | `pcie_pio` |
| Device | `10AXF40AA` (Arria 10) |
| PCIe | #1, Gen2 x8 |
| Hard IP | Arria 10 PCIe HIP, Avalon-MM, Gen2 x8 128-bit, BAR0 32-bit non-prefetchable 64 KB |
| Vendor / device ID | `0x1172` / `0xE003` |
| Configuration | volatile `.sof` over JTAG, config flash untouched |
| Status | **verified 2026-11-18** on PCB `M1003380-005`: BAR0 assigned, `A + B` test passed on Windows |

## Purpose

The design proves three things in one step:

1. The PCIe hard IP trains and the host enumerates the endpoint.
2. The host can perform 32-bit MMIO reads and writes through BAR0.
3. The FPGA actually computes the returned value (`A + B`), rather than looping
   back a host-written register.

## Register map

The register bank is built from five 32-bit Altera Avalon PIO instances. A PIO
slave occupies 16 bytes, so the registers are 0x10 apart.

| Offset | Name | Access | Description |
|--------|------|--------|-------------|
| `0x00` | `A` | RW | Operand A |
| `0x10` | `B` | RW | Operand B |
| `0x20` | `SUM` | RO | `A + B`, 32-bit, wraps on overflow |
| `0x30` | `COUNTER` | RO | Free-running 100 MHz counter |
| `0x40` | `ID` | RO | `0x50434945` |
| `0x8000`–`0xFFFF` | scratch RAM | RW | 32 KB on-chip RAM, not initialised |

`A` and `B` are write-only from the host's point of view (the PIO is an output
register). The correct `SUM` proves both writes arrived. `COUNTER` changes between
two reads; `ID` is constant.

The scratch RAM exists mainly to size BAR0: in plain Avalon-MM mode the HIP derives
the BAR0 size from the address span behind `rxm_bar0`, and the PIO bank alone would
give a 128-byte BAR0, which the Windows test driver ignores (it skips memory resources
smaller than 0x1000).

## Qsys system

`pcie_pio_sys.qsys` is generated by `make_qsys.tcl`:

- Arria 10 PCIe hard IP, `interface_type_hwtcl = Avalon-MM`, `wrala_hwtcl = 7`
  (Gen2 x8, 128-bit, 250 MHz), the same HIP mode as the upstream `PCIe1` reference
  design. Only the BAR0 Avalon-MM master (`rxm_bar0`) is connected; `txs` and `cra`
  are left unconnected.
- BAR0 is 32-bit non-prefetchable memory; BAR1–BAR5 are disabled. The size (64 KB)
  follows from the address map (see the register map above), not from
  `bar0_address_width_hwtcl`.
- Vendor/device ID `0x1172:0xE003` (Altera development-kit IDs) so the Altera PCI
  API driver can match it if one is installed later. Change these in
  `make_qsys.tcl` if you need a unique ID.
- A 100 MHz clock source drives the PIO bank and the scratch RAM; the HIP reference
  clock is the dedicated `clk_pcie1` input.

Regenerate from a PowerShell session with the Quartus environment loaded (without
it, the tools report `Unknown device part 10AXF40AA`):

```powershell
. ..\..\scripts\env.ps1
Remove-Item -Recurse -Force ip\pcie_pio_sys, pcie_pio_sys   # else save_system writes *_1.ip variants
& "$env:QUARTUS_ROOTDIR\..\qsys\bin\qsys-script.exe" --script=make_qsys.tcl --quartus-project=pcie_pio.qpf
quartus_ipgenerate pcie_pio -c pcie_pio --run_default_mode_op
```

### Why not Gen3 x8 / Avalon-MM with DMA

Until 2026-11-18 this project used `Avalon-MM with DMA`, `wrala_hwtcl = 0` (Gen3 x8,
256-bit). That mode forces BAR0 to 64-bit prefetchable memory and also enables a 64-bit
prefetchable BAR2. On the lab host Windows assigned neither BAR (problem code 10). Plain
Avalon-MM offers Gen3 at most x4 (`wrala_hwtcl = 2`). At the time the lab host was
limited to Gen2 by its BIOS (link speed Auto); with the BIOS set to Gen3 the slot trains
Gen3 x8 (see [lab-log/2026-11-18-pcie-gen3-bios.md](../../lab-log/2026-11-18-pcie-gen3-bios.md)),
so a Gen3 variant of this design is now worth testing. See
[lab-log/2026-11-18-pcie-pio-bar0-32bit.md](../../lab-log/2026-11-18-pcie-pio-bar0-32bit.md).


Or directly:

```powershell
quartus_sh --flow compile pcie_pio.qpf -c pcie_pio
```

The first build of the PCIe HIP takes about 24 minutes on this machine. The
resulting `.sof` is about 36 MB.

## Program

```powershell
..\..\scripts\program.ps1 -Sof output_files\pcie_pio.sof
```

This is a volatile JTAG load. **Do not write the configuration flash.** A power
cycle restores the factory Microsoft image (`1414:B204`).

## Host-side test

### Linux (recommended)

Bind the endpoint to `vfio-pci` or use `uio_pci_generic`, enable memory space, and
use `pcimem`:

```bash
sudo lspci -nn | grep 1172
sudo setpci -s 02:00.0 COMMAND=0x6
sudo pcimem /sys/bus/pci/devices/0000:02:00.0/resource0 0x00 w 0x12345678
sudo pcimem /sys/bus/pci/devices/0000:02:00.0/resource0 0x10 w 0x11111111
sudo pcimem /sys/bus/pci/devices/0000:02:00.0/resource0 0x20 r
# expect 0x23456789
sudo pcimem /sys/bus/pci/devices/0000:02:00.0/resource0 0x40 r
# expect 0x50434945
```

Read `0x30` twice; the counter must change.

### Windows (custom test driver)

`driver/` contains a KMDF test driver for `PCI\VEN_1172&DEV_E003`. It maps BAR0
with `MmMapIoSpace` (so 64-bit BAR addresses work), reads the ID register at
`0x40`, and exposes 32-bit read/write IOCTLs to `user/build/pcie_bar_test.exe`.
Writes are refused unless the ID matches. The driver requires test signing and
Secure Boot disabled; see [driver/README.md](driver/README.md) for the build,
sign, install and uninstall steps.

`pcie_bar_test.exe` options: no argument (read-only check), `--write` (the `A + B`
test), `--read HEX` (one register), `--temp SECONDS` (logs the `TEMP` register of
[03_pcie_gen3](../03_pcie_gen3/); this project has no `TEMP` register).

Do **not** use RWEverything to write BAR0 unless the BAR is assigned and memory
space is enabled. In this lab, writing an unassigned BAR0 through RWEverything
was followed by a host bugcheck (`0x00000050`). If you use it, read the config
space first and confirm:

- command register (`0x04`) has memory space enable set;
- BAR0 (`0x10`/`0x14`) contains a real base address, not `0x0000000C`.

A Linux live USB with `pcimem` remains a safe alternative.

## Expected observation

| Write | Value |
|-------|-------|
| `A` at `0x00` | `0x12345678` |
| `B` at `0x10` | `0x11111111` |
| `SUM` at `0x20` | `0x23456789` |
| `ID` at `0x40` | `0x50434945` |

Wrap test: `A = 0xFFFFFFFF`, `B = 0x00000001` → `SUM = 0x00000000`.

## Notes

- The card is in an x8 slot, so only PCIe #1 (lanes 0-7) can train.
- The 2026-11-17 build advertised Gen3 x8 but trained Gen2 x8, the same as the factory
  image. The cause was the host BIOS link speed (Auto = Gen2 on the lab's ASUS X99-E);
  check the BIOS and `LnkCap` vs `LnkSta` before blaming the design.
- The `.sof` is not committed. Rebuild it or use the SHA-256 above.
- If JTAG reads `0xFFFFFFFF` after a crashed programmer session, power off at the
  PSU. A Windows reboot and `FT_CyclePort` do not clear the FT232H latch.
